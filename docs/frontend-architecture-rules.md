# Dealer365 Frontend Architecture Rules

This document defines strict **frontend architecture rules** for the Dealer365 project.

All UI generated by Codex must follow these rules.

The goal is to guarantee:

- UI consistency
- predictable layout
- maintainable code
- reusable design system

shadcn/ui components provide multiple button variants and sizes, but design systems should restrict which ones are actually used to maintain consistency. :contentReference[oaicite:0]{index=0}

---

# 1 Project Folder Architecture

Dealer365 frontend must follow this structure.

app/
components/
lib/
docs/

Components structure

components
│
├ ui                # shadcn base components
├ d365
│   ├ atoms         # smallest reusable UI units
│   ├ molecules     # grouped UI components
│   ├ patterns      # reusable layout patterns
│
└ domain            # domain specific components

Example

components
 ├ ui/button.tsx
 ├ d365/atoms/icon.tsx
 ├ d365/molecules/search-toolbar.tsx
 ├ d365/patterns/workspace-layout.tsx
 └ domain/customer/customer-card.tsx

# 2 Design System Hierarchy

Dealer365 UI follows a strict hierarchy.

Design Tokens
↓
Atoms
↓
Molecules
↓
Patterns
↓
Screens

Rules

Atoms
- smallest components
- no domain logic

Molecules
- composed from atoms

Patterns
- layout structures

Screens
- assembled from patterns

---

# 3 Allowed Page Patterns

Dealer365 only allows these screen patterns.

Explorer
Workspace
Queue
Wizard
Communication
Dashboard

If a screen does not match any pattern, default to Workspace.

---

# 4 Explorer Pattern

Used for list/search screens.

Examples

Customers
Leads
Inventory
Repair Orders
Appointments

Structure

PageHeader
SearchToolbar
FilterRail
ResultTable

Rules

SearchToolbar is required  
Tables must use ResultTable  
Rows must open detail routes

---

# 5 Workspace Pattern

Used for operational screens.

Examples

Repair Order Workspace
Deal Desk
Technician Workbench
Dispatch

Structure

WorkspaceHeader
Main Content
Context Panel

Rules

Header shows entity context  
Primary action must be visible  
Context panel contains related data

# 6 Queue Pattern

Used for operational queues.

Examples

Dispatch Queue
Approval Queue
Pickup Queue

Structure

Queue Header
Queue Cards

Show status badges  
Show time indicators  
Show quick actions

# 7 Wizard Pattern

Used for multi-step flows.

Examples

Lane Check-in
Contract Generation
Appointment Booking

Structure

Step Indicator
Form Content
Footer Actions

Rules

Always show progress indicator  
Only one primary action  
Footer contains navigation actions

# 8 Component Usage Rules

Allowed sources

components/ui/*
components/d365/*
components/domain/*

Forbidden

Creating custom UI directly in screens  
Inline component creation in page files

All UI must use shared components.

---

# 9 Button System

Dealer365 uses shadcn Button as the base component.

Allowed variants

default
outline
ghost
icon

Rules

One primary button per section  
Icon buttons must use size="icon"  
No custom button sizes  
No inline color overrides

Forbidden

Random Tailwind button colors  
Multiple primary buttons  
Custom button components

---

# 10 Icon System

All icons must use the wrapper:

components/d365/atoms/icon.tsx

Allowed

<Icon icon={Search} />

Forbidden

<Search />
<FileText />

Icons must not override

strokeWidth
h-4 w-4
h-5 w-5

# 12 Layout Density

Dealer365 uses dense enterprise UI.

Spacing rules

card padding = 16px
toolbar height = 40px
button height = 32px
table row height = 40px

Avoid large whitespace.

---

# 13 Color Rules

Use theme tokens only.

Allowed

bg-primary
bg-muted
border-border
text-muted-foreground

Forbidden

hex colors
random Tailwind palette usage

---

# 14 Navigation Rules

All entity lists must open a canonical detail route.

Example

/sales/customers
/service/customers

→

/customers/:customerId

Detail pages must not be duplicated.

---

# 15 Codex Generation Rules

When Codex generates UI

1 Identify screen type  
2 Choose correct pattern  
3 Apply pattern layout  
4 Use design system components  

Never invent new layouts.

---

# 16 Refactor Rules

When refactoring existing UI

Remove ad hoc styles  
Replace raw components with design system components  
Normalize button usage  
Normalize icon usage  
Normalize typography hierarchy

---

# 17 Rule Priority

If rules conflict

Priority order

1 Frontend Architecture Rules
2 Pattern Rules
3 UI Rules
4 Component Spec
5 Local screen code
